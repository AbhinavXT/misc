## The Key Insight: One CAN Frame = One Firmware Packet

The original design on UDP used 1450-byte chunks. On CAN that breaks down because you'd need to reassemble ~24 frames into one logical chunk before you could verify the per-chunk CRC and call `Process_Firmware_Update_Messages`. That reassembly buffer adds complexity, state, and failure modes.

The right move is to shrink the chunk size so the entire firmware DATA packet — `ChunkHeader` (13 bytes) + payload — fits in one `DATA_FRAME_PAYLOAD_SIZE` (61 bytes). That leaves 61 - 13 = **48 bytes** of firmware payload per CAN frame. This is `CAN_FW_CHUNK_SIZE` in the header. The result: `Process_Firmware_Update_Messages` is called once per CAN frame with a complete, self-contained packet, just like UDP. No state machine. No reassembly. No new code in the receiver.

## Why calling `Process_Firmware_Update_Messages` from inside `ProcessIncomingCANFIFO` is dangerous

`ProcessIncomingCANFIFO` drains the FIFO in a tight `while (fifoStatus.fillLvl > 0)` loop. Right now, for each frame it calls `Process_Firmware_Update_Messages`, which includes `crcFast()` on the chunk payload, a `memcpy` into the 1 MB `gImageBuffer`, and potentially a SHA-256 + whole-image CRC at the end of the transfer. Even the light per-chunk work adds up — at ~12,300 frames, you're spending time inside the processing loop while the VCC card is still transmitting. The FIFO is only 64 messages deep. If the VCC card is transmitting at CAN-FD 5 Mbps and your MCU is spending more time processing each frame than it takes for the next frame to arrive, the FIFO fills up and starts dropping messages silently (in overwrite mode) or blocks (in blocking mode). You'd get a corrupt image with no visible error.

The fix you're describing is the standard producer-consumer pattern for exactly this scenario: the interrupt (or FIFO drain function) is the **producer** — it does nothing except copy raw bytes into a ring buffer as fast as possible, then gets out of the way. `mcan_checks()` in the main loop is the **consumer** — it reads from the ring buffer at leisure and calls `Process_Firmware_Update_Messages`. The FIFO draining stays fast, the processing happens when the CPU is free.

## Designing the ring buffer

The ring buffer needs to hold firmware packets, not raw CAN frames. Each slot should store the `pkt_msg_id` and the raw payload bytes (up to `DATA_FRAME_PAYLOAD_SIZE` = 61 bytes) along with the actual byte count — identical to what `StoreDataInSpecificRxBuffer` currently receives. A ring buffer of, say, 128 slots gives you a comfortable cushion: even if `mcan_checks` isn't called for a few main loop iterations, 128 slots of headroom means the FIFO never overflows.

The struct for each slot:

```c
typedef struct {
    uint16_t msg_id;
    uint16_t len;
    uint8_t  data[DATA_FRAME_PAYLOAD_SIZE];
} CanFwRxSlot;
```

The ring buffer itself is a statically allocated array of these slots with a write index (advanced by `StoreDataInSpecificRxBuffer`) and a read index (advanced by `mcan_checks`). Because you're bare-metal with no RTOS here, and `ProcessIncomingCANFIFO` is called from the main loop rather than from an ISR, there's actually no true concurrency — but the discipline of keeping drain and process separate is still correct and future-proofs the design if you later move the FIFO drain into an ISR.

Here is a precise walkthrough of every decision made.

**The three roles and why they're separated the way they are**

The ISR (`MCAN0_IntrISR` etc.) does the absolute minimum — it reads and clears the interrupt status register. It doesn't even touch the FIFO. This is correct and unchanged.

`ProcessIncomingCANFIFO` is called from the main loop and drains the hardware FIFO completely on every call. Its only job is to read each frame out of MCAN message RAM, extract the payload, call `StoreDataInSpecificRxBuffer`, and immediately acknowledge the FIFO slot so the hardware can reuse it. The acknowledgement (`MCAN_writeRxFIFOAck`) happens inside the loop right after the copy — this is important because it frees the hardware slot as quickly as possible, minimising the window during which a fast transmitter could overflow the hardware FIFO.

`mcan_checks` is also called from the main loop and processes **one** ring buffer slot per call. The deliberate choice to process one slot rather than drain the entire ring keeps the main loop responsive — `ethernet_checks` and `Check_And_Write_Firmware` still get called on every iteration. The ring buffer (128 slots) provides the temporal decoupling between the two: even if `mcan_checks` is occasionally delayed, there's enough headroom that `StoreDataInSpecificRxBuffer` won't overrun.

**Why the ring buffer write index is advanced last**

Inside `StoreDataInSpecificRxBuffer`, the slot is fully populated (`msg_id`, `len`, `data[]`) before `gFwRxWriteIdx` is incremented. This ordering matters because `mcan_checks` uses `FW_RX_RING_EMPTY()` which compares `gFwRxWriteIdx == gFwRxReadIdx`. If the write index were advanced before the data was copied, there's a theoretical window where `mcan_checks` could see the new index, read the slot, and find stale or partial data. Since you're bare-metal with no RTOS and `ProcessIncomingCANFIFO` and `mcan_checks` are both called from the same main loop thread (not from an ISR), this is not actually a race condition today — but the ordering discipline is correct and would remain correct if you ever moved FIFO draining into an ISR.

**The `gFwRxDropped` counter**

This is purely a diagnostic aid. In normal operation it should remain zero — 128 ring slots is more than double the hardware FIFO depth of 64, so overrun requires `mcan_checks` to be starved for the time it takes to fill both the hardware FIFO and the entire ring, which would mean the main loop is blocked for an unreasonably long time. If you ever see `gFwRxDropped` incrementing in testing, it's a signal that something else in the main loop is blocking for too long, not that the ring buffer is undersized.
